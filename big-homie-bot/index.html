Big Homie Bot

The Discord bot for the Brass Knuckle Gang server. It checks a new member against the club roster so an admin can approve them with one tap, and it sorts bug reports so an admin can file them with one tap too.

This page walks through how it works, so someone comfortable with a little Python and a Linux command line can follow along. It has been running in the gang's Discord since late October. I have trimmed the code to the parts that matter, so treat the snippets as the idea, not a drop-in copy of my files.

Just for fun. I built this because it was fun, and I post write-ups like this to give you ideas for your own projects. I can't help you build your own version or troubleshoot it, so please read this as inspiration, not a support page. Have fun with it, and 73!

The idea

Everyone in the gang's Discord wears the same nickname format: first name, callsign, gang number, and an OG tag if they hold one. New people come in with a starter role called Lil' Homies and get moved up to Homie once someone confirms they are on the roster. With well over a thousand members on that roster, looking each one up by hand is slow and easy to get wrong.

So the bot does the looking up. The member sets their nickname and types one command. The bot checks the nickname against the roster and hands an admin a finished request with buttons on it.

  1. NicknameMember sets it in the gang format
  2. /readyMember runs one command
  3. RosterBot checks callsign, number and name
  4. AdminsRequest posts with Approve and Deny
  5. RoleOn approval, Lil' Homies becomes Homie

The rules I settled on:

  • The bot never approves anyone. It checks and reports. A person presses the button.
  • The bot never decides an OG tag. If OG is involved, the admin picks "Approve + OG" or "Approve without OG".
  • One callsign, one Discord account. A callsign that is already linked to another member in the server gets stopped and flagged.
  • Change the nickname, start over. If the nickname changes after it was submitted, the request is void.
  • A bad roster download never replaces a good one. The bot keeps the last copy that made sense.
Part 1

Checking the nickname

The format is strict on purpose, so one pattern can read it. Mine looks like Justin | N9HO | #32 | AL OG. A member without an OG tag stops after the number.

NICK_RE = re.compile(
    r"^(?P<name>[^\W\d_]+(?:['’\-][^\W\d_]+)*)"
    r" \| (?P<call>[A-Za-z0-9]{3,10})"
    r" \| #(?P<num>[0-9]+)"
    r"(?P<ogs>(?: \| [A-Za-z]{2,5}(?:/[A-Za-z]{2,5})* OG)*)$"
)

If the nickname does not fit, the bot does not just say no. It tells the member what is off: a missing space beside a |, a number without the #, a callsign in lower case. That reply is private, so nobody gets corrected in front of the whole server.

If it does fit, three things have to agree with the roster: the callsign is on it, the gang number belongs to that callsign, and the first name matches. Names with accents also match their plain spelling, so nobody has to hunt for a special character on a phone keyboard.

Testing tip. I kept the checking code in its own file with no Discord in it. That means I can test a nickname from the command line and see exactly what the bot would say, without touching the server.
Part 2

Keeping the roster fresh

The club publishes its roster as a JSON feed, the same data that draws the roster on bkg.club. The bot downloads it once an hour and saves a copy to disk, so a restart or a feed outage does not leave it empty-handed.

A download only replaces the saved copy if it looks sane. If the new roster is tiny, or has lost more than a fifth of its members since the last one, something is wrong with the feed and the bot keeps what it had.

if new.member_count < 100 or (old and new.member_count < old.member_count * 0.8):
    raise RuntimeError("roster looks wrong; keeping the old copy")

After three failed refreshes in a row it posts a warning in the admin channel. And if a member's callsign is not found, the bot pulls a fresh roster once before answering, since brand new members are the ones most likely to be running the command. That extra download is limited to once a minute.

Part 3

What the admins see

A passing request lands in a private admin channel as one card: the nickname the member set, the roster entry with a link to their QRZ page, the checks that passed, and anything that needs a second look. Under it are the buttons. Deny opens a small form for a reason, and the bot sends that reason to the member so they know what to fix.

The buttons have to keep working after the bot restarts, even on a request posted days ago. Discord's Python library handles that if each button carries its own ID with the member's Discord ID inside it:

class ApproveButton(discord.ui.DynamicItem[discord.ui.Button],
                    template=r"bkg:approve:(?P<uid>[0-9]+)"):
    def __init__(self, user_id):
        super().__init__(discord.ui.Button(
            label="Approve", style=discord.ButtonStyle.success,
            custom_id=f"bkg:approve:{user_id}"))
        self.user_id = user_id

    @classmethod
    async def from_custom_id(cls, interaction, item, match):
        return cls(int(match["uid"]))

When an admin approves, the bot checks one more time that the nickname is still the one that was submitted, adds Homie, removes Lil' Homies, marks the card with who approved it, and sends the member a welcome message. Pending requests and callsign links live in a small JSON file next to the bot.

Part 4

The /bug command

The gang has a website, a membership system behind it, and this bot, and things break. I wanted one place for reports to land. Anyone in the server can type /bug and get a two-box form: what went wrong, and where.

My first version just posted the report in the admin channel. One of the other admins asked for more: have the bot take a first guess at which part is broken, then let an admin turn the report into a GitHub issue on the right repo. So now, before posting, the bot sends the report to a small AI model (Claude Haiku) with one question: is this the website, the backend, or Discord? It gets back a guess, a one-line reason and a short title.

The report lands in the admin channel with four buttons: File: Website, File: Backend, File: Discord bot, and Not a bug. The bot's guess is the green one. An admin presses a button, the bot opens the issue on that repo, and the post gets a link to it.

area = str(data.get("area", "")).strip().lower()
if area not in AREAS and area != "unclear":
    return None        # not one of the answers I asked for, so no guess

The guards matter more than the feature:

  • The model suggests, a person files. Same rule as approvals. An admin can press a different button than the green one.
  • No guess is fine. If the AI call fails or times out, the report still posts, just without a suggestion.
  • The report is data, not orders. The model is told to classify the text and ignore any instructions in it, and the bot only accepts one of four fixed answers back.
  • Nothing private goes to GitHub. The issue carries the report and the reporter's callsign, never a Discord ID, because one of the repos is public.
  • No ping-spam. The post can only ping the one admin role, and each person can send one report a minute.

It costs a fraction of a cent per report, and it needs two more secrets next to the Discord token: an API key for the model and a GitHub token that can only create issues.

Part 5

Keeping it running

The bot is two Python libraries, discord.py and aiohttp, in a virtual environment on a small Linux box at home. It does not need Docker. A systemd service starts it at boot and brings it back ten seconds after any crash:

[Unit]
Description=Discord role bot
After=network-online.target
Wants=network-online.target

[Service]
User=you
WorkingDirectory=/home/you/bot
EnvironmentFile=/home/you/bot/.env
ExecStart=/home/you/bot/.venv/bin/python bot.py
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target

A Discord bot connects out to Discord, the way a web browser connects out to a website. Nothing connects in, so there are no ports to open on the router and nothing new exposed to the internet.

The token is the whole key. Anyone who has the bot's token can act as the bot. Mine sits in a .env file that only my own login can read, along with the other keys, and that file is in .gitignore so it never reaches GitHub. The saved member data stays out of the repo the same way.

Things I would tell you before you start

  • The bot's own role has to sit above every role it hands out in the server's role list, and it needs Manage Roles. Mine checks this at startup and says so in the log.
  • Keep a person in the loop. The bot checks and a human approves, so a mistake in my rules cannot hand out a role by itself.
  • Register commands to your one server instead of globally. They show up right away, which makes testing much less confusing.
  • Write the .gitignore before the first commit, not after.
  • Make the bot tell people exactly what is wrong. A good error message is one less question for an admin.
